# Контекст проекта

Автоматизация подготовки тренажёра ЕГЭ по информатике для школы umschool.
Заказчик — помощник преподавателя, пишет код не сам: всю разработку ведёт Claude.

Две линии работы. **Отбор** — сейчас основная. **Публикатор** — дописан почти
полностью, поставлен на паузу.

## Линия 1. Отбор актуальных заданий (текущая задача)

В тренажёре около 2000 заданий, примерно по 60 на каждый из 27 прототипов.
Нужно оставить **по 15 на прототип**, для №27 — **10**, недостающее добрать.

Правила отбора:

- Актуальным считается задание, **тип** которого встречался на реальном ЕГЭ
  **с 2025 года**. Дословного совпадения не требуется: старое задание актуально,
  если подобный тип выпадал.
- Для заданий **24–26** окно шире — с 2021 года, но берём только важное:
  совсем лёгкие отсеиваем, ориентир — тенденция последних лет.
- Источники, считающиеся реальным ЕГЭ: демоверсии, досрочные волны, ЕГКР,
  основные волны, резервы, пересдачи.
- **Ничего не удаляется.** Неактуальное отмечается галочкой в рабочей таблице.
- Кандидаты на замену — чужие задания из базы umschool. Их там много (на
  прототипе №1 — 193 против ~60 своих), и это проще, чем переносить задания с
  реального ЕГЭ: снимает вопрос авторских прав.
- Задание №1 уже пересобрано, служит контрольной проверкой методики.

Важная тонкость: **тема в базе и тип задания — разные оси**. Тема отвечает на
вопрос «что спрашивают» (длина дороги, сопоставление со звёздочками), а отбор
идёт по «как решается» (уникальные степени, симметрия, соседи соседей, вилка).
Для прототипа №1 различие вообще видно только на картинке, текст у задач почти
одинаковый — там нужен либо человек, либо модель со зрением.

Темы ведутся аккуратно, но ошибки в разметке встречаются: в истории изменений
видно, как у задачи меняли и тему, и номер задания.

## Линия 2. Публикатор (пауза)

Пайплайн: парсинг задачи с kompege → разбор через Gemini → правка в диалоге →
публикация в админку umschool. Работает, кроме двух селекторов второго экрана
(поля ответа и подсказок). Вернуться к нему после отбора — понадобится, когда
будем добавлять новые задания.

Возможное упрощение: у umschool есть API, отдающий задачу целиком вместе с
подсказками и ответами. Если он принимает POST, весь браузерный `uploader` с
Playwright и Froala заменяется HTTP-запросом. Не проверено.

## Источники данных

### kompege.ru — эталон актуальности (публичный, без авторизации)

- Задача по номеру: `GET https://kompege.ru/api/v1/task/<номер>`
- Список задач прототипа: отдаётся при нажатии «Найти все задачи» на
  `https://kompege.ru/task`. Точный URL уточнить в DevTools.
- Поля: `taskId` — номер задачи на сайте (**не** `id`, там UUID), `number` —
  номер задания ЕГЭ (1–27), `key` — **ответ** (не `answer`), `text` — условие в
  HTML, `comment` — источник **с датой**: «Пересдача 08.07.26», «Резерв
  22.06.26», «Основная волна 19.06.26». Год берётся отсюда разбором строки.
- `files` — вложения (.txt, .ods, .odt) для заданий 9 и 24–27.
- Формулы приходят исходным LaTeX: KaTeX рендерит на клиенте.

### umschool — рабочая база (нужна сессия)

- Задача и список: `GET https://old.umschool.net/api/materials/tasks/`
  с фильтрами `?id=`, `?course_type_task_number=`, `&limit=&offset=`,
  пагинация по полю `next`.
- Отдаёт всё: `title` (условие), `solution`, `tips` (подсказки), `variants`
  (ответы), `class_type_topic` (тема), `course_type_task_number` (прототип и
  список всех его тем), `difficulty`, `for_generation`, `checked_by_expert`.
- История изменений: `GET /api/materials/genericlog/basetask/?id=<id>` — видно,
  кто и что правил, включая смену темы. В старых версиях условий встречается
  маркер «Задание с реального ЕГЭ», позже вычищенный из текста.
- Прототип №1 = `course_type_task_number=943`, код `ninf-1`.
- Админка на Django + Froala. Публикация двухшаговая: сначала задание, ответ —
  на следующем экране.

## Правила работы

- **Читаю свободно, пишу только по явной команде.** В `auth_state.json` лежат
  рабочие куки — это доступ к админке под именем заказчика. Ничего не
  публикуем, не правим и не удаляем в umschool по своей инициативе; любая
  запись — сначала вхолостую (`--dry-run`), потом с подтверждения.
- Разработку ведём в ветке `claude/python-task-automation-system-gro2pr`.
- Заказчик отвечает на вопросы по типам заданий — спрашивать нужно, экспертное
  суждение остаётся за ним. Модель сортирует и обосновывает, а не решает.
- Любой вердикт об актуальности должен опираться на конкретные задания:
  «тип встречается в основной волне 2025 и досрочной 2026», а не «неактуален».
  Проверяются доказательства, а не мнение.
- Лимиты Claude ограничены. Массовую работу с картинками разумно отдавать
  Gemini (у заказчика Google One), локальные модели на RTX 5070 — только для
  механических проходов, не для суждений.

## Модули

| файл | назначение |
| --- | --- |
| `umschool.py` | выкачивание базы umschool в JSONL |
| `review_pages.py` | HTML-страницы просмотра с отметками и выгрузкой CSV |
| `scraper.py` | парсинг задач с kompege (API, браузер как резерв) |
| `attachments.py` | распаковка .ods, .odt, .csv, .txt для промпта |
| `formatting.py` | Markdown и LaTeX → чистый текст и HTML для платформы |
| `llm_processor.py` | Gemini: разбор задачи, диалоговая правка, уникализация |
| `review.py` | правка разбора в диалоге перед публикацией |
| `uploader.py` | публикация в админку, `--inspect` и `--detect` для селекторов |
| `auth_state.py` | ручной вход и сохранение сессии |
| `main.py` | оркестратор публикаторского пайплайна |

Ключевые ловушки, на которые уже наступали: `taskId` против `id` у kompege,
`key` против `answer`, три редактора Froala с одинаковым селектором
`div.fr-element` (различать по `>> nth=`), `#title` в админке — это
«Максимальный балл», а условие лежит в `textarea[name="title"]`.
